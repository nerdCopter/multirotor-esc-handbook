# AM32 Multi-Rotor ESC Technical Reference Guide

AM32 is a modern, modular, open-source 32-bit ESC firmware created by AlkaMotors for ARM Cortex-M0/M4 and RISC-V architectures (STM32F051, STM32G071, AT32F421, AT32F415, GD32, and others). It has become the primary open-source successor to legacy closed-source firmware like BLHeli_32.

## 2. Advanced Parameters & Technical Architecture

### Dynamic PWM Modes & "PWM by RPM"
AM32 offers three distinct PWM frequency modulation strategies:
1. **Fixed PWM Frequency (e.g. 24kHz / 48kHz):** Constant switching frequency across the entire operational band.
2. **Variable PWM by Throttle (Low/High Bounds):** Scales switching frequency proportionally to input throttle commands.
3. **Variable PWM "By RPM":**
   * Dynamically modulates the MOSFET switching frequency based directly on real-time measured motor angular velocity (electrical RPM) rather than static stick input — this avoids the mid-throttle mechanical/electrical resonance ("jello") that fixed-by-throttle variable PWM can produce.
   * **Sourced mechanism**, in the AM32 creator's own words (interview with Joshua Bardwell, [yOeVj6P9PSU](https://youtu.be/yOeVj6P9PSU)): fixed at **24kHz** until commutation frequency reaches roughly **11.5kHz**, then ramps linearly up to **48kHz**. Below that threshold, the lower switching rate keeps BEMF zero-crossing sampling windows wide and active-braking torque high; above it, the higher rate reduces stator eddy-current losses and acoustic whine.
   * BLHeli_32 shipped an equivalent feature starting in **firmware v32.8.3** ([xuQeJA4EGr8](https://youtu.be/xuQeJA4EGr8)).
   * **Real-world caveat (unverified community reports, Discord — not independently confirmed):** the creator's own framing above is entirely positive, but at least two independent users have reported the opposite experience on AM32 specifically — one describing "major desync problems" with both throttle-based Variable PWM and By-RPM PWM, resolved by switching to fixed 24kHz; another describing "horrible low Hz noise" (nicknamed "the blob of death" in that report) from default Variable mode, and finding By-RPM "a bit slow" to respond, preferring fixed 48kHz instead. Don't treat By-RPM as a strict upgrade over fixed frequency — it's one more setting worth A/B testing on your specific build, not a universal fix.

### Sinusoidal Startup (FOC-lite)
* When starting from a dead stop, AM32's Sine Start mode drives all three phases with open-loop sinusoidal waveforms; since BEMF sensing is unavailable in this mode, throttle directly controls rotation speed rather than duty cycle.
* **There is no fixed universal RPM handoff figure to trapezoidal commutation.** AM32 ramps the sine-mode speed to match the minimum speed required at changeover, and the `prot_stall` (stall-protection ERPM threshold) setting can be raised to give the motor a longer sinusoidal run-up. See the [AM32 ESC Settings Explained wiki](https://github.com/AlkaMotors/AM32-MultiRotor-ESC-firmware/wiki/ESC-Settings-Explained) for the authoritative behavior.
* **Usage Context:** Essential for rock crawlers and low-speed robotics. For high-speed FPV racing/freestyle quads, traditional trapezoidal open-loop spoolup is typically preferred to minimize initial spin-up latency. Fixed-speed and fixed-duty-cycle throttle modes are not compatible with sinusoidal startup.

### Commutation Timing — AM32 Has No Demag Compensation Setting
* **Timing Angle:** Configurable in finite degree steps (typically `15°` to `26°`, default `22.5°` or `Auto`).
* **Sourced tuning guidance** (Chris Rosser, [3SHzyUaypFw](https://youtu.be/3SHzyUaypFw)): **15°** as a safe universal default across 3"/5"/7" motors — not size-tiered the way BLHeli_32 is elsewhere in this KB. **7.5°** is usable for racing only if the build stays desync-free at that setting. **0° is demonstrated to desync** in his own test data (the motor loses control entirely under acceleration) — this is observed failure, not just a caution.
* **AM32 has no Demag Compensation or Demag Timing setting.** The full field list of the AM32 web configurator: Bootloader/MCU info, Essentials, Motor (Stuck rotor protection, Stall protection, Use hall sensors, Complementary PWM, Auto timing advance, PWM Type), Timing advance, Startup power, **Motor KV**, **Motor poles**, Beeper volume, PWM Frequency, Extended settings (Ramp rate, Minimum duty cycle), Limits, Current control, Sinusoidal Startup, Brake, Servo settings — no field labeled Demag, Demag Compensation, or Demag Timing appears anywhere in it.
* **If you're desyncing on AM32, don't look for a Demag dial — it isn't there.** Check instead that **Motor KV** and **Motor poles** (see below) are set to your motor's actual values, and that Timing Advance isn't set too low (see the demonstrated-desync data above) — those are AM32's real levers for this class of problem.

### Motor KV & Motor Poles
Two real, confirmed fields in the AM32 configurator (verified directly against the UI) — these are the closest thing AM32 has to BLHeli_32's Demag Compensation, since AM32 derives its protection behavior from them rather than exposing a separate manual dial:
* **Motor KV:** functions like BLHeli_32's Rampup Power (lower value → more low-RPM current/torque available). Must be set to the motor's actual KV rating; round down if the exact value isn't listed as an option. Sourced (Chris Rosser, [3SHzyUaypFw](https://youtu.be/3SHzyUaypFw)): this matters most on low-KV big builds (8"/10", motors around 900/800/400KV) — AM32's default assumption is roughly 2000KV, which under-drives a low-KV motor and causes poor acceleration until this is corrected to match the actual motor.
* **Motor poles:** the motor's actual magnet pole count. Used, along with Motor KV, by AM32's Low RPM Throttle Protect (see below) instead of a fixed RPM threshold. Get both values right before assuming a desync is a firmware tuning problem — a mismatched KV/pole count can itself cause the exact symptoms this KB attributes elsewhere to Demag/timing issues on other firmwares.

### Hardware Protection & Current Limiting
* **Maximum Current Limiting:** Configurable maximum peak current ceiling using on-board shunt resistor ADC telemetry to prevent blown FETs on prop strike or locked-rotor conditions.
* **Temperature Protection:** Thermal throttling cutoff based on internal MCU or NTC sensor readings.
* **Stall Protection:** Automatically disengages power when zero-crossing detection fails for a predefined number of electrical cycles.
* **Low RPM Throttle Protect:** sourced difference (interview with the AM32 creator, [yOeVj6P9PSU](https://youtu.be/yOeVj6P9PSU)): BLHeli's version of this protection uses a fixed RPM threshold, while AM32's is derived from the motor's pole count and Kv instead of a flat number — relevant if you're porting settings from a BLHeli-family ESC.
